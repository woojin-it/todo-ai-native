## 1. 배경과 문제

현재 앱은 `frontend/`만 있고, 할 일은 `App.tsx`의 React 상태(`useState`)에만 저장된다.
UI(작업 카드, 완료율, 접근성, 반응형)는 완성되어 있지만 다음 문제가 있다.

- 새로고침하거나 다른 기기로 접속하면 할 일이 모두 사라진다.
- 사용자를 구분하지 않는다.
- 서버 측 입력 검증과 오류 처리가 없다.

이 PRD의 목표는 두 가지다.
**(a)** 현재 UI 동작을 회귀 없이 보존하고,
**(b)** FastAPI와 Supabase를 붙여 사용자별 할 일을 영속 저장한다.

## 3. 요구사항 ID 체계

- `FR-xxx`: 기능 요구사항. `NFR-xxx`: 비기능 요구사항(품질 속성).
- `D-x`: 이 PRD에서 확정한 설계 결정(5절).
- 하위 문서는 이 ID를 **그대로 인용**한다. 수용 기준은 `AC-<요구사항 ID>-<번호>`, 작업은 `T-xx`로 쓴다.
- 새 요구사항은 이 문서에 먼저 추가한 뒤 하위 문서에 반영한다. ID는 재사용하지 않는다.

## 4. 범위

### 4-1. 포함

- 할 일 생성, 조회, 수정, 완료 토글, 삭제와 영속 저장
- 할 일 마감일 등록·수정·삭제와 표시 (FR-012)
- 할 일 카테고리(업무·개인·학습) 지정과 카테고리별 목록 필터 (FR-013, FR-014)
- 할 일 우선순위(높음·보통·낮음) 지정과 화면의 우선순위순 정렬 (FR-015, FR-016)
- 완료 상태(전체·진행 중·완료) 필터, 카테고리 필터와 AND 조합 (FR-017)
- 완료율 표시 (현재 `ProgressMeter` 동작 유지)
- 사용자별 데이터 격리 (dev 인증 → Supabase Auth 순서로 단계 도입)
- 서버 입력 검증, 공통 에러 포맷, 로딩·오류 UI
- 현재 접근성·반응형·디자인 시스템 보존
- Vercel 배포

### 4-2. 제외

- 로그인·회원가입 화면의 세부 UX와 소셜 로그인 (3단계에서 별도 결정, 9절)
- 공유·협업, 태그 등 새 데이터 필드 (마감일은 v2.1, 카테고리는 v2.2, 우선순위는 v2.4에서 범위에 포함, FR-012·FR-013·FR-015)
- 우선순위 필터, 정렬 기준 전환(토글)·생성순 보기, 서버 측 정렬(`?priority=`, `?sort=`), 사용자 정의 우선순위 단계
- 사용자 정의 카테고리(추가·이름 변경·삭제), 카테고리 여러 개 지정
- 마감 시각(시:분), 마감 알림, 마감일순 정렬·필터
- 오프라인 지원, 실시간 동기화(Supabase Realtime), 알림
- 페이지네이션, 검색, 카테고리·완료 상태 외 필터(마감일·우선순위 등), 서버 측 완료 상태 필터(`?completed=`), 사용자 지정 정렬(드래그). API는 생성 순서로 반환하고 화면은 우선순위순으로 보여 준다 (카테고리 필터는 v2.2, 우선순위 정렬은 v2.4, 완료 상태 필터는 v2.5에서 범위에 포함, FR-014·FR-016·FR-017)
- 단건 조회 API (`GET /api/todos/{id}`). UI가 쓰지 않음

## 5. 설계 결정 (D-x)

| ID | 결정 | 이유 |
| --- | --- | --- |
| D-1 | 단계별로 도입한다. 1단계 백엔드와 In-Memory 저장소, 2단계 Supabase 영속 저장, 3단계 Supabase Auth, 4단계 배포 | 단계마다 동작하는 상태를 유지하고, 인증 UI가 없어도 영속 저장을 먼저 검증할 수 있다 |
| D-2 | 1~2단계 인증은 dev 모드다. `Authorization: Bearer <token>`의 토큰 값을 그대로 `user_id`로 쓴다 | 인증 UI 없이 API와 사용자 격리 로직을 테스트할 수 있다 |
| D-3 | 2단계의 `todos.user_id`는 `text`로 두고 `auth.users` FK를 걸지 않는다. 3단계에서 `uuid` + FK로 바꾼다 | dev 토큰(`dev-user` 등)은 UUID가 아니므로 FK를 걸면 INSERT가 실패한다 ([spec-review.md](./spec-review.md) R-01) |
| D-4 | **dev 인증 상태로는 공개 배포하지 않는다.** 공개 URL 배포는 3단계 완료 후에만 한다 | dev 토큰은 누구나 위조할 수 있다 (NFR-004) |
| D-5 | 백엔드는 Supabase Secret Key(`SUPABASE_SECRET_KEY`)로 PostgREST에 접근한다. 소유자 필터는 서버 코드가 1차로 맡고, RLS는 2차 방어선이다 | Secret Key는 RLS를 우회한다 |
| D-6 | 다른 사용자의 할 일에 접근하면 403, 없는 할 일이면 404를 반환한다 | id가 추측하기 어려운 UUID라 존재 노출 위험이 낮고, 오류 원인 구분이 디버깅에 유리하다 |
| D-7 | 완료율은 서버에 저장하지 않고 프론트에서 `todos`로 계산한다 | 파생 값은 상태로 중복 저장하지 않는다 (CLAUDE.md 6-1) |
| D-8 | 마감일은 시각 없이 **날짜만**(`YYYY-MM-DD`) 저장한다. "오늘", "지남" 판단은 브라우저의 현지 날짜로 한다 | 시각을 저장하면 UTC 변환 때문에 날짜가 하루 밀릴 수 있다. 개인 할 일에는 날짜 단위면 충분하다 |
| D-9 | 카테고리는 고정 3종 `work`(업무), `personal`(개인), `study`(학습) 중 **정확히 하나**다. 필수 값이고 생략하면 `personal`이다. 기존 데이터도 `personal`로 채운다 | 선택 항목으로 두면 "카테고리 없음" 상태가 생겨 필터가 4종이 된다. 고정 목록이면 DB `check` 제약과 화면 라벨을 단순하게 유지할 수 있다 |
| D-10 | 필터 API는 `GET /api/todos?category=`(선택)로 제공하지만, 화면은 전체 목록을 한 번 받아 **브라우저에서 거른다**. 필터 상태는 저장하지 않는다(새로고침하면 "전체") | 필터를 바꿀 때 요청이 없고, 낙관적 업데이트·롤백 기준(`confirmedRef`)이 목록 하나로 유지된다. 할 일이 500건 이하라는 전제(NFR-007)에서 충분하다 |
| D-11 | 우선순위는 고정 3단계 `high`(높음), `medium`(보통), `low`(낮음) 중 **정확히 하나**다. 필수 값이고 생략하면 `medium`이다. 기존 데이터도 `medium`으로 채운다. DB는 `priority text not null default 'medium'` + `check` 제약 | 카테고리(D-9)와 같은 구조라 검증·DB 제약·라벨 관리가 단순하다. "우선순위 없음"을 따로 두면 정렬 위치가 모호해진다 |
| D-12 | 우선순위 정렬은 **브라우저에서 항상** 적용한다. 높음 → 보통 → 낮음, 같은 우선순위 안은 생성순(안정 정렬)이고 완료 여부는 순서에 영향이 없다. 정렬 결과는 상태로 저장하지 않는 파생 값이다. API(`GET /api/todos`)는 생성순 그대로 반환하고 정렬 파라미터를 두지 않는다 | D-10과 같이 목록 하나를 받아 화면에서 가공한다. `todos` 상태를 생성순으로 유지해야 삭제 복구 위치·추가·롤백 규칙(NFR-006)이 그대로 동작한다 |
| D-13 | 완료 상태 필터(전체·진행 중·완료)는 **화면 전용**이다. 카테고리 필터와 AND로 적용하고(카테고리 → 상태), API 파라미터(`?completed=`)와 DB 변경은 두지 않는다. 상태 필터 개수는 현재 카테고리 안에서 세고, 완료율은 카테고리 필터 결과 기준이다(상태 필터와 무관). 필터 상태는 저장하지 않는다 | D-10과 같이 받아 둔 목록 하나를 거르면 되고, 화면이 쓰지 않을 서버 파라미터를 미리 만들지 않는다. 완료율을 상태 필터 결과로 계산하면 "완료"는 항상 100%, "진행 중"은 항상 0%라 의미가 없다 |

## 7. 기능 요구사항 (FR)

| ID | 요구사항 | 현재 구현 |
| --- | --- | --- |
| **FR-001** | 사용자는 텍스트를 입력해 할 일을 추가한다. 앞뒤 공백을 제거한 뒤 1~100자여야 하며, 비었거나 공백만 있으면 추가할 수 없다. 규칙을 어기면 요청하지 않고 입력창 아래에 이유("할 일 내용을 입력해 주세요." / "할 일은 100자 이하로 입력해 주세요.")를 보여 준다. 새 할 일은 미완료 상태로 생성되며, 화면에서는 같은 우선순위 묶음의 맨 끝에 붙는다(FR-016). | `TodoInput`, `App.addTodo` |
| **FR-002** | 사용자는 본인 소유의 할 일 전체를 조회한다. API는 생성 순서(오름차순)로 반환하고, 화면 순서는 FR-016을 따른다. 할 일이 없으면 다음 행동을 안내하는 빈 상태를 보여 준다. | 빈 상태 구현됨, 서버 조회 없음 |
| **FR-003** | 사용자는 체크박스로 할 일의 완료 상태를 토글한다. 완료된 할 일은 취소선과 완료 색상(`--pine`)으로 구분한다. | `TodoItem`, `App.toggleTodo` |
| **FR-004** | 사용자는 할 일 텍스트를 그 자리에서 편집해 저장하거나 취소한다. 저장 규칙은 FR-001과 같다. 텍스트가 바뀌지 않았으면 저장 요청을 보내지 않는다. Esc를 누르면 취소된다. | `TodoItem` 편집 모드 |
| **FR-005** | 사용자는 할 일을 삭제한다. 이미 삭제된 할 일을 다시 삭제하려 해도 사용자에게는 성공으로 보인다. | `App.deleteTodo` |
| **FR-006** | 시스템은 완료율을 "N개 중 M개 완료" 문장, 퍼센트, 원형 프로그레스로 표시하고, 전체·완료·미완료 개수를 통계 카드로 보여 준다. 할 일이 24개 이하면 원을 할 일 하나당 한 칸(호)으로 나누고(칸 순서는 화면의 목록 순서와 같다), 24개를 넘으면 연속형 원을 쓴다. 모두 완료하면 "N개 모두 완료"로 표시한다. 완료율과 통계는 상태 필터와 무관하다. | `ProgressRing`, `StatCard` (spec-review R-48) |
| **FR-007** | ToDo API는 인증된 요청만 처리한다. 1~2단계는 dev Bearer 토큰, 3단계는 Supabase Auth JWT를 쓴다. 인증이 없거나 올바르지 않으면 401을 반환한다. | 없음 |
| **FR-008** | 할 일은 소유자(`user_id`)별로 격리한다. 다른 사용자의 할 일은 조회, 수정, 삭제할 수 없다. | 없음 |
| **FR-009** | 생성, 수정, 토글, 삭제 결과는 서버 저장소에 즉시 반영되어 새로고침 후에도 유지된다. 2단계부터 Supabase PostgreSQL에 저장한다. | 없음 |
| **FR-010** | 서버는 할 일 텍스트를 다시 검증한다(공백 제거 후 1~100자, 문자열 타입만 허용). 실패하면 `VALIDATION_ERROR`를 반환한다. DB 제약이 최종 방어선이다. | 없음 |
| **FR-012** | 사용자는 할 일을 추가할 때 마감일(날짜)을 선택해 등록할 수 있고, 편집 모드에서 마감일을 바꾸거나 지울 수 있다. 마감일은 선택 항목이다. 카드에는 "M월 D일 마감"으로 표시하고, 오늘이면 "오늘 마감", 지났고 미완료면 "N일 지남"으로 강조한다. 날짜는 2000-01-01~2100-12-31 범위의 실제 날짜만 허용한다. | 없음 (v2.1 신규) |
| **FR-013** | 사용자는 할 일을 추가하거나 편집할 때 카테고리(업무·개인·학습) 하나를 고른다. 기본값은 "개인"이며, 필터가 특정 카테고리일 때는 그 카테고리가 기본값이다. 카드에는 카테고리 이름을 표시한다. 서버는 `work`, `personal`, `study` 외의 값을 거부한다. | 없음 (v2.2 신규) |
| **FR-014** | 사용자는 목록 위의 필터(전체·업무·개인·학습)로 해당 카테고리의 할 일만 본다. 각 필터에는 할 일 개수를 표시하고, "전체"가 기본이다. 완료율(FR-006)과 빈 상태는 현재 필터의 목록 기준으로 계산한다. API는 `category` 쿼리 파라미터로 같은 필터를 제공한다. | 없음 (v2.2 신규) |
| **FR-015** | 사용자는 할 일을 추가하거나 편집할 때 우선순위(높음·보통·낮음) 하나를 고른다. 기본값은 "보통"이고, 추가에 성공해도 선택은 유지된다. 카드에는 카테고리 다음에 우선순위를 글자로 표시하며 "높음"만 굵게 강조한다(새 색 없음). 서버는 `high`, `medium`, `low` 외의 값(대소문자·공백 변형, `null` 포함)을 거부한다. | 없음 (v2.4 신규) |
| **FR-016** | 화면의 할 일 목록은 항상 우선순위순(높음 → 보통 → 낮음)으로 보여 준다. 같은 우선순위 안에서는 생성 순서를 유지하고, 완료 여부는 순서에 영향을 주지 않는다. 카테고리 필터(FR-014)와 함께 적용되며, 완료율 막대의 칸 순서도 같다. 우선순위를 바꾸면 카드가 새 위치로 옮겨지고 포커스는 그 카드의 "수정" 버튼으로 돌아온다. 정렬 전환(토글)은 없다. | 없음 (v2.4 신규) |
| **FR-017** | 사용자는 카테고리 필터 아래의 완료 상태 필터(전체·진행 중·완료)로 미완료 또는 완료한 할 일만 본다. "전체"가 기본이고, 카테고리 필터와 **함께(AND)** 적용된다. 각 버튼에는 현재 카테고리 안의 개수를 표시한다. 완료율(FR-006)은 상태 필터와 관계없이 카테고리 필터 결과 기준이다. "진행 중"·"완료" 필터에서 체크해 카드가 빠지면 포커스는 새 할 일 입력창으로 가고, "완료" 필터에서 할 일을 추가하면 상태 필터는 "전체"로 돌아간다. 서버 API는 바뀌지 않는다(D-13). | 없음 (v2.5 신규) |
| **FR-011** | 프론트는 목록을 불러오는 동안 로딩 상태를, 실패하면 오류 메시지와 "다시 시도" 버튼을 보여 준다. 목록을 불러오기 전에는 추가할 수 없다. 개별 동작이 실패하면 `role="alert"` 알림으로 알린다. | 없음 |

## 8. 비기능 요구사항 (NFR)

| ID | 요구사항 |
| --- | --- |
| **NFR-001** | 접근성: 체크박스는 네이티브 `<input type="checkbox">`, 작업 텍스트는 연결된 `<label>`을 쓴다. 수정·삭제 버튼의 `aria-label`에 작업 내용을 넣는다. 완료율 문장은 `aria-live="polite"`, 오류 알림은 `role="alert"`로 전달한다. |
| **NFR-002** | 반응형: 360px 이상에서는 작업 버튼을 한 줄에 두고, 359px 이하에서는 다음 줄로 내린다. 터치 기기(`pointer: coarse`)에서는 버튼 높이를 44px 이상으로 한다. 가로 스크롤은 생기지 않아야 한다. |
| **NFR-003** | 포커스 관리: 편집을 저장하거나 취소하면 해당 작업의 "수정" 버튼으로 포커스를 되돌린다. 삭제 후에는 새 할 일 입력창으로 옮긴다. 추가 후에도 입력창에 포커스를 둔다. 모든 조작 요소는 `:focus-visible` 링을 표시한다. |
| **NFR-004** | 보안: `SUPABASE_SECRET_KEY`는 백엔드 환경 변수에만 둔다(프론트 `VITE_*`와 저장소 금지). 모든 쿼리에 소유자 조건을 명시하고 RLS를 켠다. dev 인증으로는 공개 배포하지 않는다(D-4). |
| **NFR-005** | 배포: 프론트는 Vercel 정적 호스팅, 백엔드는 Vercel 서버리스 함수로 각각 배포한다. 백엔드는 인증 없이 호출할 수 있는 `GET /api/health`를 제공한다. |
| **NFR-006** | 오류 처리와 일관성: 모든 API 에러는 공통 포맷 `{error: {code, message, details}}`로 응답하고, 메시지는 한국어로 쓴다. 토글·수정은 낙관적으로 업데이트하고, 실패하면 바뀐 필드만 롤백한다. 단, 그사이 사용자가 같은 필드를 다시 바꿨다면 롤백하지 않는다. 삭제는 먼저 제거하고, 실패하면 원래 위치에 복구한다. |
| **NFR-007** | 성능: 할 일이 500건 이하일 때 목록 조회 API는 p95 500ms 이내로 응답한다(같은 리전 기준). |
| **NFR-008** | 디자인 일관성: 새 UI는 [ui-guidelines.md](./ui-guidelines.md)의 토큰, 컴포넌트, 반응형 규칙을 따른다. 색상을 하드코딩하지 않고, 다크 모드와 `prefers-reduced-motion`을 지원한다. |
| **NFR-009** | 품질 게이트: 프론트는 `npm run build`와 `npm run lint`(경고 0건)를 통과해야 한다. 백엔드는 `pytest` 전체를 통과해야 한다. 테스트 이름에는 요구사항 ID를 넣는다. |

## 9. 성공 지표

1. 새로고침과 재접속 후에도 할 일이 100% 유지된다 (FR-009).
2. 사용자 A의 요청으로 사용자 B의 할 일을 조회·수정·삭제할 수 없다 (FR-008).
3. 현재 UI의 접근성·반응형 수용 기준이 API 연동 후에도 모두 통과한다 (NFR-001~NFR-003).
4. 품질 게이트가 통과한다 (NFR-009).
